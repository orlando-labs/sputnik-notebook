# Запуск доски, Periodic Work и HTTP Server из orbit-notebook

Архитектурный проект для Sputnik Notebook, обновлён 16 ноября 2026 года. Общий контракт поставщиков описан в [пакетных компонентах и subboard](notebook-package-components.md).

В первой версии macOS установите `slowpilot/orbit-notebook` в **Dependencies**. Для исходного пакета выберите каталог `orbit/packages/orbit-notebook` через **Install Local Package**. HTTP Server и HTTP Server Board появятся на вкладке **orbit-notebook** в палитре. Сервис работает на `127.0.0.1` и получает отдельный Bearer-токен при запуске. В инспекторе можно выбрать экспортированную функцию, которая возвращает `orbit.Routes`, или использовать маршруты пакета. Поддоска показывает результат Watch после записи во вход через `POST /reading`. Описания таблицы маршрутов, публикации за пределами loopback, установки при запуске и удалённого исполнения относятся к целевой архитектуре. [Использование пакета](../../../orbit/packages/orbit-notebook/README.md).

Доска с сервисами имеет собственную сессию исполнения. Внутри неё Periodic Work запускает задачи по расписанию, а пакетный HTTP Server принимает запросы через Orbit. Оба компонента находятся в **Services** вне сетки доски. Настройки доступны в **Object Inspector**.

## Поставка HTTP Server

HTTP Server поставляет пакет `slowpilot/orbit-notebook`, зависящий от `slowpilot/orbit`. Идентичность типа — `slowpilot/orbit-notebook:http-server`. Пакет предоставляет инструмент палитры, публичные свойства, предметную проверку и адаптер исполнения. Orbit предоставляет маршрутизацию, HTTP pipeline, `orbit.App` и `ServerHandle`.

Notebook отображает свойства существующим Object Inspector и управляет компонентом через общий контракт поставщиков. Сессия доски, установка зависимостей, секреты, разрешения, воркер, лимиты и остановка принадлежат Core. Для этого компонента не вводятся отдельный язык UI или поставляемые пакетом клиентские представления.

HTTP Server появляется в палитре **Services** после подключения поставщика к книге. Карточка рекомендованного компонента или действие **Добавить компоненты из пакета…** позволяет добавить экземпляр с ещё не установленной зависимостью. Чтение метаданных, открытие инспектора и сохранение экземпляра не импортируют код и не открывают порт. Один установленный Orbit без `orbit-notebook` не предоставляет компонент Notebook.

Поставщик входит в зависимости книги даже при отсутствии импорта в ячейках. Точные версии и digest `orbit-notebook` и `orbit` фиксируются общим lock окружения. Если пакет отсутствует или несовместим, сервис остаётся в книге с настройками и диагностикой зависимости.

Компонент можно использовать самостоятельно в Services или внутри пакетной subboard. Например, будущая Webhook Monitor может объединить его со счётчиками и таблицей событий. Такая композиция использует обычную доску; для первой поставки HTTP Server она не обязательна.

## Как пользователь работает с доской

| Действие | Что происходит |
| --- | --- |
| Открыть доску, перейти в дизайнер или предпросмотр | Видны сохранённая доска и статус её сессии. Открытие и сохранение сами по себе пассивны. |
| **Запустить доску** | Notebook проверяет сохранённую конфигурацию, запрашивает недостающие согласия и при необходимости инициализирует лист-контроллер через обычный Run. После успешной инициализации включённые сервисы стартуют автоматически. |
| **Запустить лист** | Выполняется лист-контроллер. Запуск сервисов привязан к команде **Запустить доску**, в том числе когда несколько досок используют этот лист. |
| Перейти на другую вкладку или открыть ту же доску во втором окне | Сессия продолжает работу. Во втором окне видны её фактический статус и результаты. |
| **Остановить доску** | Планировщики прекращают назначать тики, HTTP-серверы прекращают приём запросов. Текущие операции получают ограниченное время на завершение, затем Notebook отменяет оставшуюся работу и освобождает воркеры и порты. Лист и другие доски продолжают собственный жизненный цикл. |
| **Перезапустить доску** | Notebook завершает текущую сессию и запускает новую по сохранённой ревизии с повторной проверкой конфигурации и разрешений. |

В заголовке доски отображаются **Остановлена**, **Запускается**, **Работает**, **Работает с ошибками** или **Останавливается**. Рядом находится основная команда запуска или остановки. В навигации виден индикатор работающей доски, чтобы её можно было найти после переключения вкладки. В секции **Services** показываются состояние каждого сервиса и причина, если он пропущен, приостановлен или завершился с ошибкой. Статус HTTP-сервера включает фактический URL с действием **Скопировать**, число запросов и последнюю ошибку. Periodic Work показывает следующий тик и существующую историю.

При первом запуске доски, которой нужны согласия, диалог перечисляет затронутые сервисы. Отказ по одному сервису позволяет запустить остальные, если пользователь выбирает этот вариант. Ошибка инициализации контроллера завершает попытку запуска всей доски. Ошибка отдельного сервиса, например занятый порт, оставляет доску в состоянии **Работает с ошибками**. После устранения причины доступен повторный запуск сервиса в текущей сессии. Исполняемые правки применяются через **Перезапустить доску**. Сохранённое удаление сервиса или доски и отзыв разрешения останавливают затронутый сервис сразу.

Закрытие локальной книги завершает её сессии досок. Для удалённой книги сессией владеет Core Agent. Закрытие браузера или отключение клиента оставляет её активной, а повторное подключение показывает тот же статус. После перезапуска агента пользователь снова запускает доску. Для наблюдателей команды управления недоступны.

## Periodic Work

Включённое расписание стартует вместе с доской и использует существующие Fixed Delay, Fixed Rate, первый тик, Stop on Error и политику хранения истории. В активной сессии доступны **Пауза**, **Продолжить**, **Выполнить один раз** и **Очистить историю**. Ручная пауза относится к текущей сессии. **Выполнить один раз** доступно и на паузе. После остановки доски остаётся просмотр истории.

Существующие доски с Periodic Work при первом переходе на новую модель показывают, какие расписания запустятся по кнопке **Запустить доску**. Пользователь может отключить любое расписание в инспекторе до запуска. При переходе Core завершает прежние самостоятельные расписания этой доски и сохраняет доступную историю. Сохранённый локальный флаг **Pause while board is hidden** сохраняет смысл дополнительной паузы внутри активной сессии, если он включён в старой конфигурации. У новых компонентов расписание по умолчанию работает и при скрытой доске. Для удалённого исполнения видимость вкладки остаётся свойством клиента.

## HTTP Server в Object Inspector

Свойства объявляет `orbit-notebook`; Notebook использует штатные редакторы свойств, структурированных ссылок и списков. Сохранённые настройки применяются к новой сессии при запуске или перезапуске. Статус, счётчики и фактический URL являются состоянием исполнения.

| Поле | Предлагаемое поведение |
| --- | --- |
| Название и **Включён** | Определяют, как сервис виден в доске и входит ли он в следующий запуск. |
| Адрес и порт | Адрес привязки на машине, где выполняется книга. По умолчанию `127.0.0.1`. В удалённой книге это адрес на узле агента. |
| Доступ | В первой версии Bearer-токен. Инспектор принимает или создаёт токен и показывает наличие секрета. В книге хранится ссылка, а значение хранится в Keychain локально или в хранилище секретов узла. При переносе книги секрет задаётся для нового окружения. |
| Источник маршрутов | **Объект Orbit Routes** или **Таблица маршрутов**. Выбранный источник определяет конфигурацию роутера целиком. |
| Разрешённые записываемые входы | Структурированные ссылки на объявленные входы, которым обработчики сервиса могут присваивать значения. Для самостоятельного сервиса это выбранные project inputs; внутри subboard доступны входы её scope и явно разрешённые публичные связи. |

Для доступа извне loopback требуется явное согласие на выбранный адрес и защищённый HTTPS-вход, настроенный на узле исполнения. Когда адрес привязки и клиентский URL отличаются, секция Services показывает оба. Core Agent применяет политику хоста до открытия порта. Публичные временные сессии и предпросмотр остаются пассивными. Токен проверяется до вызова обработчика, включая запросы с автоматическим OPTIONS. В журналы и историю попадают статусы, счётчики и шаблоны маршрутов.

### Согласие на установку orbit-notebook и открытие порта

При запуске доски Notebook проверяет `orbit-notebook` и его зависимость `orbit` в окружении книги. Зафиксированные совместимые установленные артефакты используются повторно. Если зависимости ещё не разрешены, Notebook готовит согласованный план установки и фиксации версий. Диалог показывает `slowpilot/orbit-notebook`, его точную версию, устанавливаемую или переиспользуемую версию `slowpilot/orbit`, окружение книги и адрес, который будет слушать сервис. Установленный Orbit переиспользуется только при совместимости с выбранным поставщиком и lock. Для удалённой книги проверка и установка относятся к узлу Core Agent.

Разрешение установки и разрешение слушать адрес фиксируются отдельно, даже если интерфейс запрашивает их одним диалогом. Установка не выдаёт runtime grants. Для прослушивания нужен `net.listen` на выбранный endpoint в профиле воркера конкретного экземпляра. Остальные недостающие grants перечисляются по данным согласованного набора пакетов и конфигурации сервиса.

Если нужны установка и сетевое согласие, действия в диалоге — **Установить orbit-notebook и разрешить запуск**, **Запустить без HTTP-сервера** и **Отмена**. Первое запускает существующий процесс установки поставщика и недостающих зависимостей в окружение книги, фиксирует разрешённый граф и затем запускает сервис при действующей попытке запуска доски. Второе сохраняет конфигурацию и оставляет HTTP-сервис выключенным на текущую сессию. После отказа повторное предложение открывается по действию **Настроить доступ** в Services. Ошибка установки отображается там же с возможностью повтора. Для установки, которой требуется остановка уже работающих воркеров книги, интерфейс сначала показывает затронутые сессии и предлагает повторить операцию после их остановки. Конфликт установленной версии показывается как задача для **Dependencies**.

Установка переиспользуется всеми HTTP-сервисами книги, а сетевое согласие относится к конкретному сервису, окружению и endpoint. При смене адреса, порта или узла согласие запрашивается заново. После импорта или дублирования доски новый экземпляр сервиса проходит собственную проверку разрешений.

### Маршруты

**Объект Orbit Routes.** В инспекторе выбираются модуль книги и имя экспорта, значением которого является `orbit.Routes`. Для сервиса внутри subboard ссылки разрешаются в контексте экземпляра и его явно предоставленных внешних связей. При старте адаптер `orbit-notebook` в воркере загружает сохранённую версию модуля и проверяет тип значения. Этот режим сохраняет возможности Orbit, в том числе scopes, mounts и middleware маршрутов. Настройки доступа и записи входов применяются ко всему сервису.

**Таблица маршрутов.** Табличное свойство в инспекторе связывает HTTP-метод и URL pattern с модулем и именем экспортированной функции, методом экспортированного класса или действием контроллера Orbit. Например, `POST /readings/:id` может вызывать `api.Readings#store`. Строки хранят структурированные ссылки на объявления. Адаптер `orbit-notebook` разрешает их при подготовке воркера и строит тот же `orbit.Routes`. Orbit определяет синтаксис шаблонов, порядок совпадения и правила параметров. Инспектор проверяет полноту строк и явные дубликаты, а адаптер через Orbit проверяет шаблоны, существование и сигнатуру обработчиков. Ошибка указывает на строку свойства или на экспорт с объектом маршрутов. Правки вступают в силу при перезапуске доски. Для редактирования и сохранения таблицы код поставщика не исполняется.

## Как HTTP-запрос обновляет доску

HTTP-обработчик исполняется в воркере своего сервиса. Адаптер `orbit-notebook` предоставляет ему разрешённые операции над входами через контекст экземпляра. Для обновления данных обработчик передаёт разрешённый набор значений в Core. Core применяет существующую проверку типов, ограничений и версии принятого состояния. Например, `POST /readings/:id` записывает последнее измерение в объявленный вход `latest_reading`. После успешной записи Watch-ячейка контроллера пересчитывает сводку, а Metric или Live Chart на доске получает результат обычным путём. Manual-ячейка помечается устаревшей. Та же семантика действует для других инициализированных листов книги, которые используют этот вход.

Внутри subboard локальный `latest_reading` относится к scope конкретного экземпляра. Запись в одноимённый вход другой поддоски или родителя возможна только по явной разрешённой связи. Два экземпляра одной поддоски имеют независимые входы, каналы и состояние сервера. Адреса прослушивания остаются ресурсом узла: одинаковый явно выбранный порт приводит к обычному конфликту bind, несмотря на разные namespace.

Для первой версии обработчик формирует один пакет изменений на запрос. Воркеры передают переносимые значения по существующей границе исполнения. Core применяет пакет атомарно после успешного результата обработчика и до отправки успешного HTTP-ответа. Успешный ответ означает, что входы приняты, а пересчёт Watch может завершиться позже. Равный пакет не создаёт повторный Watch. При конфликте версии ответ `409` сообщает, что входы не изменились. При временно занятом контроллере ответ `503` позволяет клиенту повторить запрос. У такого обработчика вывод ограничен конечным ответом, чтобы результат записи был известен до начала отправки. При Stop уже принятый запрос может завершить запись до конца отведённого срока. Core отклоняет записи после истечения срока, смены поколения воркера или отзыва разрешения. Уже принятые изменения обрабатываются обычным Watch.

## Владение исполнением

- Notebook Core хранит одну активную сессию на пару книга/доска. У сессии есть идентификатор, сохранённая ревизия, фаза запуска и состояния дочерних сервисов. Повторный Start или reconnect возвращает существующую сессию. Статус и команды проходят через общий Core для macOS и web.
- Core создаёт воркер и поколение для каждого сервиса. Адаптер `orbit-notebook` загружается в контекст конкретного экземпляра, создаёт и держит `orbit.App` и `ServerHandle` на время сессии, публикует состояние и реализует остановку через операции Orbit прекращения приёма и штатного shutdown. Core контролирует срок и при необходимости отменяет воркер. Periodic Work использует существующий планировщик и механизм отмены подзадач. Общая установка пакета не означает общий изменяемый объект сервера.
- Сервис внутри subboard принадлежит её дочерней области в сессии родительской доски. Остановка доски или удаление поддоски завершает её HTTP-сервисы. Сворачивание поддоски меняет отображение. Наблюдение и команды адресуют стабильный путь экземпляра, поэтому reconnect и второе окно не создают новый сервер.
- Черновики и новые сохранённые версии видны в редакторе. Работающая доска показывает ревизию запуска и индикатор **Нужен перезапуск** при изменении исполняемых настроек. Удаление и отзыв доступа проверяются отдельно по актуальному состоянию книги.
- `project.json` хранит экземпляр пакетного компонента: ссылку на тип поставщика, версию схемы свойств, настройки и ссылки на модули, входы и секреты. Версии пакетов фиксируются общим lock. Состояние сессии, разрешения узла и актуальные URL отслеживает владелец исполнения. Клиент, поддерживающий оболочку пакетного компонента, сохраняет неизвестные поля; более старый клиент отклоняет неподдерживаемую версию книги. Для доски с новой моделью Core проверяет наличие активной сессии при любой команде исполнения сервиса, включая команды прежнего API. Новый клиент проверяет возможности поставщиков и сессий доски в Core перед запуском удалённой доски.

## Порядок будущей реализации и приёмка

1. **Общий контракт поставщиков и сессия доски.** Подготовить обнаружение метаданных, оболочку сохраняемого экземпляра, штатный инспектор и зависимость без импорта в коде. Провести Start, Stop и наблюдение через Core и общий интерфейс доски, включая Periodic Work. Проверить открытие без выполнения и установки, отсутствующего поставщика с сохранением настроек, независимый Run листа, два окна одной доски, две доски с одним контроллером, остановку во время тика и восстановление статуса после reconnect.
2. **Поставка orbit-notebook, HTTP-воркер, установка и доступ.** Реализовать свойства и адаптер в пакете, подключить общий установщик, проверку grants, хранилище секретов и жизненный цикл Orbit. Проверить отказ без установки и открытого порта, установленный Orbit без поставщика, переиспользование совместимых пакетов, конфликт lock, занятый порт, неверный токен, отзыв доступа, освобождение порта после Stop и доставку статуса удалённым клиентам. Предметные обработчики Orbit остаются в пакете; Core и клиенты используют общий контракт компонента.
3. **Оба источника маршрутов и Watch.** Подключить выбор экспорта и табличное свойство маршрутов. Проверить функцию, метод класса, действие контроллера и ошибочный target. Сквозной сценарий проходит от запроса с токеном через принятие входа и Watch до обновления показателя на доске. Проверить равные значения, конфликт версии, запрет записи необъявленного входа и остановку при активном запросе.
4. **Композиция в subboard.** После общего механизма поддосок проверить два экземпляра с одинаковыми локальными именами и разными разрешёнными endpoint, независимое состояние и явные связи с родителем. Остановка или удаление одной поддоски затрагивает только её сервисы. Готовый Webhook Monitor может стать примером из `orbit-notebook`; его создание не блокирует самостоятельную поставку HTTP Server.

До реализации стоит проверить на коротком техническом прототипе, как отдельный worker удерживает `ServerHandle` между командами, как выдаётся grant на конкретный bind без расширения прав книги, и как применить входы из запроса через владельца Core без ожидания под его блокировкой.
