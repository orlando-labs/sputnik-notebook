# Пакетные компоненты, subboard и инспекторы значений

Архитектурный проект от 16 ноября 2026 года. В macOS реализована первая версия пакетной палитры, сервисов и поддосок. Ниже зафиксирована целевая архитектура, включая инспекторы возвращаемых значений.

## Пакетная палитра macOS

Установите каталог `orbit-notebook` через **Dependencies → Install Local Package**. При открытии Board Designer в палитре появится цветная вкладка **orbit-notebook**. Таким же цветом выделены её плитки **HTTP Server** и **HTTP Server Board**. Сервис добавляется в Services, а поддоска размещается в выбранной строке. Удаление пакета скрывает его вкладку. Уже сохранённые экземпляры показывают состояние недоступности.

Пакет может объявить отдельные дополнения для Notebook в справочном поле `notebook_packages` своего `sputnik.build.yaml` или `sputnik.build.json`. Dependencies показывает рекомендации из манифестов всех установленных пакетов книги, включая транзитивные зависимости. Установка дополнения проходит отдельным действием через обычный установщик. Orbit рекомендует `orbit-notebook`, а `orbit-notebook` объявляет Orbit своей зависимостью.

Первая версия macOS читает статический ресурс `notebook/components.json` из установленных артефактов книги. Для поддоски пакет поставляет `project.json` обычной книги с одной доской. В каждой позиции родительской доски Swift открывает отдельный экземпляр обычного контроллера и его входов. Текущий интерфейс не содержит редактора публичных связей с родительской доской. Сервисы стартуют по **Start Board** в отдельных процессах Sputnik. [Пакет orbit-notebook](../../../orbit/packages/orbit-notebook/README.md).

## Единица расширения

Обычный пакет Sputnik может поставлять компоненты и инспекторы значений Notebook. Экземпляр пакетного компонента имеет публичные свойства, собственный контекст исполнения и опциональное представление в виде обычной доски. Инспектор значений расширяет существующий Result Inspector на листе и доске и может поставляться самостоятельно.

| Форма | Состав и размещение |
| --- | --- |
| Невизуальный компонент с инспектором | Свойства, логика их связи с кодом, команды и состояние. Сервисный компонент, например HTTP Server, находится в Services своей доски и не занимает колонки. |
| Subboard | Те же свойства и контекст плюс внутренняя доска со своими строками, компонентами, входами, контроллером и сервисами. Размещается в сетке родительской доски. |

Subboard использует существующие компоненты и формат доски. Эта архитектура не вводит отдельный декларативный язык UI, деревья новых виджетов или поставляемые пакетом Vue/SwiftUI-представления. Метаданные свойств нужны существующему Object Inspector, а визуальную часть пакет собирает как обычную доску.

Пакет может поставлять несколько типов компонентов и вариантов их начальной настройки. Например, `orbit-notebook` предоставляет HTTP Server как невизуальный сервис; позднее тот же пакет может предоставить subboard Webhook Monitor с сервером, счётчиками и таблицей событий. Такая поддоска является отдельным примером композиции, а не условием использования HTTP Server.

## Определение, инструмент палитры и экземпляр

| Сущность | Ответственность |
| --- | --- |
| Определение типа | Публичные свойства, версия их схемы, адаптер исполнения и, при наличии, определение внутренней доски. Принадлежит пакету. |
| Инструмент палитры | Название, категория, справка и начальные настройки создаваемого экземпляра. Несколько инструментов могут создавать один тип. |
| Экземпляр | Стабильный ID, свойства, внешние связи, размещение и собственные данные в конкретной книге. Принадлежит книге. |

Тип идентифицируется канонической идентичностью пакета и локальным именем, например `slowpilot/orbit-notebook:http-server`. Источник пакета учитывается существующим механизмом зависимостей. Совпадение отображаемых названий не делает типы взаимозаменяемыми. Перенос типа между пакетами требует явного преобразования ссылок.

Для preset, который только вставляет обычные компоненты и не требует кода поставщика после вставки, допускается сохранить результат как обычную структуру доски. Полноценный пакетный компонент сохраняет связь со своим определением и его версией.

## Поставка и обнаружение

Поставщик объявляется в существующем `sputnik.build.yaml` / JSON-манифесте. Объявление ссылается на метаданные компонентов и инспекторов значений, а также на ресурсы обычных досок внутри пакета. Эти файлы входят в штатный inventory и проверку целостности артефакта. Модули контроллеров и адаптеров поставляются обычным механизмом Sputnik.

Метаданные описывают тип и инструменты палитры, публичные свойства, допустимое размещение, требуемую версию API компонентов Notebook, ссылки на определение поддоски и код адаптера. Точный набор полей остаётся частью будущего контракта. Версия API Notebook, версия пакета и версия схемы свойств различаются.

Палитра объединяет встроенные инструменты и поставщиков, явно подключённых к книге. Транзитивная зависимость сама по себе не добавляет инструменты. В удалённой книге каталог доступных поставщиков формирует Core Agent по окружению исполнения.

Подключение пакетного компонента становится явной зависимостью книги даже при отсутствии импорта в исходниках. Ссылки на поставщиков входят в корни разрешения зависимостей и существующий lock окружения. Отдельного установщика или lockfile компонентов нет. Один выбранный пакет и его зависимости переиспользуются экземплярами книги в рамках совместимого графа.

Действие **Добавить компоненты из пакета…** позволяет найти поставщика и подключить его. Для рекомендованных компонентов, включая HTTP Server, Notebook может показывать карточку поставщика в каталоге. Просмотр карточки и сохранение экземпляра с отсутствующей зависимостью не устанавливают пакет. Подготовка запуска может предложить штатную установку с точными версиями и окружением назначения.

Палитра и Object Inspector читают статические метаданные без импорта модулей и выполнения инициализаторов пакета. Открытие книги, создание экземпляра, раскрытие поддоски и сохранение конфигурации пассивны. Предметная проверка, которой нужен код пакета, выполняется в контексте явной команды подготовки или запуска, отдельно от отображения инспектора.

## Публичные свойства и связь с кодом

Свойства являются публичным API экземпляра. Пакет задаёт их типы, значения по умолчанию, ограничения и описания; существующий Object Inspector отображает поддерживаемые редакторы свойств. Важны ссылки на экспорт модуля, вход, секрет и списки структурированных записей, например строки маршрутов HTTP Server. Это метаданные свойств, без описания произвольного расположения UI-элементов.

Пакет владеет логикой увязки свойств и кода. Адаптер или контроллер преобразует принятую конфигурацию в объекты библиотеки, разрешает ссылки и организует взаимодействие внутренних частей. Например, адаптер Orbit создаёт `orbit.Routes` и `orbit.App` по настройкам сервиса. Для этого не требуется переписывать пользовательские ячейки или вставлять сгенерированный код в сохранённый лист.

| Категория | Семантика |
| --- | --- |
| Сохранённые свойства | Конфигурация экземпляра. Влияющие на исполнение изменения применяются через явный запуск или перезапуск; работающий экземпляр показывает необходимость перезапуска. |
| Входы исполнения | Объявленные изменяемые значения с типами, Apply, принятым состоянием и существующей семантикой Watch/Manual. |
| Выходы и состояние | Опубликованные результаты, каналы, статус, счётчики и ошибки. Их получение не меняет сохранённые настройки. |
| Действия | Явные команды экземпляру с проверкой прав и принадлежности текущей сессии. |

Публичное свойство может содержать ссылку на вход, если значение должно меняться во время исполнения. Это позволяет отделить, например, адрес прослушивания с перезапуском от управляющего входа, который обрабатывается обычным Apply.

Инспектор проверяет типы, ограничения и структуру данных. Core повторяет эти проверки перед принятием изменений. Предметную семантику, например допустимость Orbit target или шаблона маршрута, проверяет адаптер пакета. Ошибка адресуется конкретному свойству или записи списка.

## Инспекторы возвращаемых значений

Пакет может предоставить предметное представление для значения, которое ячейка возвращает обычным способом. На листе оно доступно в компоненте результата под ячейкой, а на доске — в Result Inspector, привязанном к этой ячейке. Оба используют один снимок того же запуска. Object Inspector по-прежнему редактирует настройки компонента, включая выбор источника и предпочтительного представления для карточки доски. [Существующий просмотр результатов](notebook-result-viewer.md).

Поставщик объявляет ID инспектора, его название, поддерживаемые типы и ссылку на адаптер. Тип сопоставляется по идентичности класса в разрешённом графе пакетов с учётом пакета, модуля и экспортируемого типа. Notebook выбирает среди инспекторов поставщиков, подключённых к книге. Если подходящих инспекторов несколько, Result Inspector предлагает выбор и сохраняет стандартный режим по умолчанию, пока пользователь не выберет предпочтительный. Явная привязка хранит ID поставщика и инспектора и учитывается в зависимостях книги, даже если код ячейки импортирует только библиотеку типов. Инспектор можно поставить вместе с библиотекой или отдельным пакетом.

Адаптер получает возвращённое значение в среде исполнения ячейки при подготовке результата Run или Watch. Он формирует ограниченные по размеру данные для штатного представления Notebook, например структурированного дерева, таблицы или изображения. Пакет определяет, какие данные извлечь и как их сгруппировать. Например, инспектор тензора может показать форму, тип элементов, устройство и небольшую выборку значений. В состав результата входят идентичность инспектора и версия формата его представления. Клиенты отображают эти данные существующими средствами просмотра.

Адаптер работает в окружении запуска с его разрешениями. Контракт требует чтения значения без его изменения, а подготовка представления учитывает бюджеты времени и объёма. Core проверяет данные перед публикацией. Ошибка, превышение лимита, отсутствующий поставщик или неподдерживаемый формат отображаются рядом с обычным результатом Inspect/Pretty. Успех вычисления ячейки от дополнительного представления не зависит.

Открытие результата, переключение представления и просмотр на доске читают уже подготовленный снимок. Они не перезапускают ячейку, не устанавливают пакет и не выполняют адаптер на клиенте. Добавление инспектора после запуска даёт новое представление при следующем вычислении. Снимок привязан к ревизии и запуску и наследует правила хранения и метку предыдущего результата. Исторический снимок можно открыть поддерживаемым просмотрщиком без исходного объекта и версии пакета, которая его создала. Живой объект и обратные вызовы воркера через границу представления не передаются.

## Поддоска и компоновка

Определение subboard включает обычную доску, определения её входов, контроллер и необходимые ресурсы пакета. Она может содержать вложенные поддоски и сервисы. Notebook создаёт экземпляр внутренней структуры со стабильными локальными ID; пакетный код не требуется для построения её исходной сетки в дизайнере.

В родительской сетке subboard занимает одну позицию с обычным span от 1 до 12. Внутри работает самостоятельная сетка со своими строками. Внутренние строки не смешиваются со строками родителя: поддоска может занимать любую высоту в пределах общих бюджетов документа и исполнения.

- При автоматической высоте родительская строка учитывает высоту содержимого поддоски.
- При фиксированной доступной высоте внутреннее содержимое прокручивается.
- Размеры вложенных компонентов считаются от внутренней ширины поддоски.
- Сервисы принадлежат своей доске, находятся вне её строк и сохраняются при перестановке или удалении визуальных строк.
- Существующие ограничения глубины, числа компонентов и ресурсов учитывают вложенное содержимое, чтобы упаковка в subboard не обходила бюджеты книги.

Notebook рисует общую оболочку поддоски: собственный заголовок с именем экземпляра, рамку или отличающийся фон, обозначение принадлежности пакету и, при наличии исполнения, его состояние. Доступны сворачивание и переход к инспектору экземпляра. Сворачивание управляет отображением, а остановка выполняется явной командой жизненного цикла.

Редактор родительской доски управляет размещением и публичными свойствами экземпляра. Внутренним составом владеет пакет; обновление его определения выполняется через обновление зависимости. Превращение внутренней структуры в собственную редактируемую доску может быть отдельной будущей операцией создания копии.

## Scope экземпляра и namespace

Каждый экземпляр получает собственную область имён. Она охватывает входы, внутренние компоненты, каналы графиков, таблиц и изображений, действия, сервисы, контроллеры, историю и принадлежащие экземпляру данные. Ссылки на ресурсы пакета разделяются по правилам неизменяемого артефакта; изменяемые данные принадлежат экземпляру.

Идентичность объекта определяется цепочкой стабильных ID экземпляров и его локальным ID. Отображаемые заголовки не входят в идентичность. Переименование и перемещение между строками одной родительской доски сохраняют связи. Дублирование создаёт новые идентичности экземпляров и независимые области; активные воркеры, поколения и выданные согласия не копируются.

Внутри пакета автор использует локальные имена вроде `port`, `requests` и `last_event`. Контекст экземпляра разрешает их в соответствующей области, включая вложенные subboard. Простая конкатенация отображаемых имён не является контрактом идентичности.

Поддоска получает собственный экземпляр контроллера и изменяемое состояние, создаваемые при явном запуске. Два экземпляра одного определения не разделяют mutable globals только потому, что импортируют один модуль пакета. Адаптер должен создавать состояние для конкретного контекста; это требование распространяется на библиотеки и кэширование внутри поставщика.

Существующая семантика `notebook.input` как доступа к project input сохраняется. Для локальных входов поддоски нужен явный доступ через контекст экземпляра; точный API будет определён отдельно. Автоматического поиска одноимённого входа в родительской области нет.

## Публичные связи с родителем

Поддоска предоставляет публичные свойства, входы, выходы и действия. Внешние компоненты связываются с этим интерфейсом через инспектор экземпляра. Внутренние ID не становятся автоматически доступными родителю.

Каждая связь имеет структурированную ссылку, тип и явное направление передачи. Например, вход `topic` получает значение от входа родительской доски, выход `last_message` используется её показателем, а действие `reconnect` вызывается кнопкой. Разрешение на запись во внешний вход задаётся отдельно от разрешения читать его значение.

Core разрешает связи в соответствующих scope, проверяет типы и применяет изменения через общий механизм принятых входов. Сохраняются атомарность пакета изменений, контроль версии, тихое принятие равных значений и Watch/Manual. Связи участвуют в общей проверке зависимостей; автоматический пересчёт не должен создавать неограниченный цикл через границы поддосок.

Через границы контроллеров и воркеров передаются поддерживаемые переносимые значения и опубликованные снимки. Ссылки на mutable VM-объекты, сокеты и `ServerHandle` остаются у владельца исполнения. Доступ к project inputs и секретам книги предоставляется через явно разрешённые ссылки в контексте экземпляра.

## Владение исполнением

| Участник | Ответственность |
| --- | --- |
| Пакет | Определение компонента или поддоски, публичные свойства, предметная проверка, контроллер и адаптация к библиотеке. |
| Notebook Core | Каталог поставщиков для окружения, зависимости, принятие конфигурации и входов, сессии, воркеры, разрешения, лимиты, команды, остановка и наблюдение. |
| Клиенты macOS и web | Палитра, существующий Object Inspector, отображение обычных компонентов и оболочки subboard, доставка команд и состояния. |

Сервисный адаптер поддерживает подготовку, запуск, публикацию состояния, объявленные команды и остановку с ограниченным сроком. Core предоставляет контекст экземпляра и контролирует его действительность. Контекст содержит идентичность сессии и поколения, сохранённую конфигурацию, разрешённые ссылки на входы и секреты, публикацию состояния и сигнал отмены.

Сервисы владеют своими воркерами. Визуальный компонент может читать опубликованные данные без отдельного воркера; визуальная вложенность сама по себе не определяет размещение процессов. Все контроллеры, сервисы и подзадачи имеют однозначного владельца в дереве экземпляров.

Поддоска входит в сессию родительской доски как дочерняя область. Start подготавливает нужные контроллеры и включённые сервисы; Stop завершает дочернее исполнение. Удаление экземпляра и отзыв доступа останавливают затронутое поддерево. Ошибка частного контроллера блокирует его поддерево и отражается в состоянии родительской доски; остальные независимые части могут продолжать работу.

Загрузка адаптеров и инициализация модулей происходят в рамках явного исполнения после проверки зависимостей и разрешений. Установка пакета не выдаёт grants. Core и воркер применяют фактические ограничения с учётом политики хоста и полномочий экземпляра. Вложение в другую доску не расширяет права. После отзыва разрешения или смены поколения Core отклоняет поздние записи и команды.

Клиенты наблюдают одно состояние через Core. Два окна и повторное подключение не создают копии работающего экземпляра. Локальное закрытие книги завершает её исполнение; удалённой сессией владеет агент, и отключение клиента само по себе её не останавливает. После перезапуска владельца автоматическое восстановление heap и запуск сервисов не предполагаются.

## Сохранение и обновление

Книга сохраняет ссылку на тип поставщика, версию схемы свойств, стабильный ID экземпляра, свойства, внешние связи, размещение и ссылки на собственные данные. Определение внутренней доски берётся из зафиксированной зависимости. Изменяемые данные экземпляра хранятся отдельно от неизменяемых файлов пакета.

Принятые значения входов и состояние исполнения остаются у владельца исполнения по существующей политике хранения. Сохранение доски не превращает текущие значения в defaults. Открытые сокеты, активные URL, воркеры и grants не являются переносимой конфигурацией; выбранные адрес и порт сохраняются как свойства сервиса. В книге сохраняются ссылки на секреты, а их значения остаются в хранилище соответствующего окружения.

Формату проекта нужна известная Notebook оболочка пакетного компонента, которую можно структурно проверить и сохранить без установленного поставщика. Внутри неё конфигурация поставщика сохраняется без потери неизвестных полей и точности чисел. Текущий запрет неизвестных component kinds потребуется изменить для этой оболочки.

При отсутствии пакета, несовместимой версии API или недоступном определении экземпляр остаётся на месте с заглушкой и причиной. Пользователь может исправить зависимость или удалить экземпляр; сохранение других объектов не теряет его настройки. Старый клиент, который вообще не поддерживает оболочку, отклоняет новую версию книги с сообщением о необходимости обновления.

Обновление поставщика выполняется явно через Dependencies и общий lock. Пакет предоставляет преобразования между версиями схемы свойств и при необходимости собственных данных; стабильные локальные ID позволяют сопоставлять внутреннюю структуру. Изменения принимаются после успешной проверки и миграции с сохранением исходного состояния при ошибке. Открытие книги не выполняет миграционный код. Работающий экземпляр сохраняет установленную ревизию и поколение до явного перезапуска.

## Первое применение и будущая приёмка

Первым поставщиком служит `orbit-notebook`, зависящий от `orbit`: [проект HTTP Server](notebook-http-server.md). Он проверяет общий контракт невизуального компонента, Object Inspector, разрешений и сервисного адаптера. Отдельный пример subboard проверит вложенную компоновку, публичные связи и изоляцию двух экземпляров; им может стать Webhook Monitor из того же пакета.

Будущая реализация должна подтвердить следующие сценарии:

1. Пакет поставляет компонент напрямую или через отдельный пакет-адаптер; добавление поставщика не требует нового предметного обработчика в клиентах и Core.
2. Открытие книги, палитры и инспектора, вставка и сохранение экземпляра не исполняют код и не устанавливают зависимости.
3. Поставщик учитывается в зависимостях и lock даже при отсутствии импорта; удалённая книга использует окружение агента.
4. Два экземпляра одной subboard, включая вложенные экземпляры с одинаковыми локальными именами, независимо изменяют входы, состояние контроллера, каналы и сервисы.
5. Автоматическая высота, фиксированная высота с прокруткой, span и сворачивание сохраняют границы внутренней сетки и явную оболочку.
6. Публичные связи сохраняют типы, атомарность, Watch/Manual и отсутствие неявного доступа к родительским входам; битая связь имеет адресуемую диагностику.
7. Stop, удаление, отзыв разрешения и смена поколения завершают нужное поддерево и отклоняют поздние операции; reconnect наблюдает тот же экземпляр.
8. Отсутствующий пакет переживает открытие и сохранение книги; явное обновление мигрирует конфигурацию и данные либо сохраняет прежнее состояние при ошибке.
9. Обычный возврат значения поддерживаемого типа даёт пакетное представление на листе и привязанной доске. Оба показывают снимок одного запуска. Выбор представления и просмотр истории пассивны. При ошибке адаптера, превышении лимита или отсутствии поставщика остаётся стандартный результат.

Документ не назначает числовую версию нового формата или сигнатуры API. Их следует определить вместе с общей реализацией поставщиков, scope и сессий, сохранив описанные границы ответственности.
