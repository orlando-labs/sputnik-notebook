## 1. P1 — полный результат выполнения и авторские display-компоненты

**Подтверждённый недочёт:** часть уже существующих runtime-данных теряется при
проекции в web. `summary_json` в `packages/notebook-core/native/host.cpp:43`
содержит progress, но `apps/notebook-web/backend/execution.s:50` его не включает
в DTO ячейки. `nb_core_presentation_snapshot` в `host.cpp:90` экспортирует только
table/displays/images. Live charts, stopwatch и locals для metric-binding
в общий codec входят, но веб-проекция их не выдаёт. Признак `unsupported` в
`host.cpp:122` учитывает неподдержанные MIME и audio, поэтому отсутствие charts
или таймера само по себе не даёт предупреждения о неполноте результата.

`frontend/src/NotebookCellInputs.vue:8` выводит только Input и Parameter Form.
Сохранённые pre/post metric/live_chart/table/image/audio остаются в документе,
но по их авторским настройкам не отображаются. Автоматический вывод таблиц и
изображений в `NotebookRichOutput.vue:10` не заменяет такие компоненты.

Осталось:

- Расширить ограниченные по размеру публичные DTO для progress, stopwatch,
  charts и значений, доступных для привязок; сохранить точность чисел.
- Сделать общий renderer авторских компонентов для ячеек и будущих boards,
  привязки по ID/имени, состояния unavailable/stale и настройки в inspector.
- Перенести семантику расположения pre/post, управления видимостью исходника
  и устранения дублирующего автоматического вывода по примеру Swift.
- Audio вынести в отдельный медиасрез, явно сообщая о его отсутствии до переноса.

Критерий: один пример из Swift с progress, таймером, metric и live chart выдаёт
те же значения при live-обновлении, после завершения и переподключения. Авторские
настройки переживают save/export/import; неподдержанный компонент виден как
недоступный, а не исчезает.

## 2. P1 — boards: просмотр, затем конструктор

В `frontend/src/NotebookWorkspace.vue:268` boards представлены только текстом
«N boards preserved». Нет открытия board, раскладки или исполнения её UI.
Swift-референс: `tools/notebook-macos/NotebookBoardView.swift` и
`NotebookBoard.swift`.

Сначала нужны навигация и чтение существующих boards: controller sheet,
строки/колонки, размеры и выравнивание, groups/tabs/split и общие компоненты из
пункта 1. Затем — палитра, создание/редактирование/дублирование, inspector,
перестановка и Undo/Redo. Каждый шаг требует проверки light/dark и узкого экрана
с теми же иерархией, отступами и состояниями, что в Swift.

Критерий: существующий Swift `.sputnikbook` открывает board с узнаваемой
структурой, работающими привязками и параметрами; просмотр сам не запускает код.
Конструктор меняет тот же формат без потери неизвестных настроек.

## 3. P1 — actions, periodic services и управление исполнением на board

`backend/execution.s:90` принимает только `run` и `run_all`; web-маршрутов для
service.configure/list нет. В core уже есть board actions, изолированные миры
invocation, серверное расписание и durable receipts
(`packages/notebook-core/src/notebook/core.s:536`, `:839`, `:866`).

Нужны публичные DTO/ACL и UI Action, Execution Controls, Periodic Work:
Run Once/Start/Pause/Clear, состояние последнего/текущего запуска, ошибка,
Stop/Force Stop и восстановление команды. Планирование остаётся в core.

Критерий: сервис продолжает работать после закрытия вкладки; повтор запроса
с тем же ID не создаёт второго запуска; открытие board не включает расписание.
Семантика — по [remote actions/watch](notebook-remote-inputs-watch-actions.md).

## 4. P2 — текст и удобство редактора

`NotebookWorkspace.vue:325` использует textarea, а `:327` явно оставляет
форматированные text cells только для чтения. Нужны renderer и редактор rich text,
подстановки переменных, подсветка Sputnik и диагностикa. Отдельно остаются

Черновик исходников/файлов и неопределённая команда Save сейчас живут в памяти
вкладки (`NotebookWorkspace.vue:32`); есть защита ухода и ручной экспорт. Для
восстановления после сбоя браузера нужен отдельный локальный журнал черновика,
привязанный к аккаунту, проекту и базовой ревизии. Журналы команд параметров и
исполнения уже существуют и эту задачу не заменяют.

## 5. P2 — медиа и оставшиеся компоненты ввода

Не перенесены audio player/waveform/управление и экспорт, запись audio input,
image input и annotators, file input как принятое runtime-значение, date/time,
presets и selection bindings компонентов. Загрузка ресурса в проект уже есть,

file input локальным исполнением. Их следует планировать как расширение общего
remote-контракта, а не только перенос Vue-компонента.

## 7. P2 — история запусков и сравнение экспериментов

30 октября: 4h.2 реализован. Публичный snapshot сохраняет точные scalar JSON,
источники ячеек, revision/module references, bounded rich results и provenance
окружения/настроек/пакетов. Pin/Rename имеют отдельные метаданные и CAS; Delete
защищает текущие, активные и pinned результаты, расход времени не сбрасывается.
Comparison считает точные числовые delta и экспортирует CSV. Restore показывает
один scalar scope и предупреждает о Watch, затем использует обычный atomic Apply.
[Проверка](../evidence/2026-10-30/notebook-web-run-history/README.md).
Ниже сохранён исходный gap для контекста.


Сейчас есть список запусков/результаты и экспорт сохранённой ревизии
(`NotebookHistory.vue:11`). Нет Swift-подобных Inspect snapshot, Pin/Rename/Delete,
сравнения inputs/metrics с delta и экспорта сравнения, восстановления параметров.
Swift-референс — `NotebookRunHistoryView.swift:24` и `:54`.

Сначала нужен отдельный публичный неизменяемый snapshot запуска: источники,
принятые параметры, provenance окружения и результаты. Приватный core run record
не следует отдавать целиком. Восстановление параметров должно отдельно показывать,
что будет принято и вызовет ли это Watch. ZIP исходников не включает установленные
серверные пакеты или подготовленное окружение и сам по себе не воспроизводит их.

## Завершение переноса и документация

После функциональных срезов нужен сквозной набор примеров Swift → web → Swift
для каждого поддержанного компонента, сверка light/dark/mobile и текущая матрица
возможностей. README содержит устаревшие вводные: строки 29, 60 и 71 называют
модули, package UI или inputs будущими срезами, хотя поздние разделы описывают
готовую реализацию.

Для эксплуатации нужен проверяемый запуск реального `backend/main.s` с core и
assets/reverse proxy, без fixture OAuth. Инструкция уже есть в
`apps/notebook-web/README.md:265`; `tools/smoke_server.mjs` явно является тестовым
оркестратором, включая его режим `production` (он означает production assets).
Готовность preview не доказывает готовность такого развёртывания.
