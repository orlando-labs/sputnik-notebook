# Палитра компонентов Sputnik Notebook: анализ и предложения

Исходный анализ: 14 октября 2026 года. Реализация P0/P1: 15 октября 2026 года. Ревью оставшегося scope: **20 октября 2026 года**.

Основание: рабочий код macOS-приложения, инженерная документация и сохранённые UI-превью от 13 октября. Документ сохраняет исходный анализ и реализованные этапы P00, P0 и P1. Текущие решения по оставшемуся scope, зависимостям и аудио собраны в [ревью перед P2](notebook-components-p2-review.md). Текущая реализация P2 и ограничения описаны в [журнале этапов](notebook-p2-implementation.md). Исходный анализ выполнялся без запуска приложения и пользовательских проектов. Реализация P00/P0/P1 проверяется на временных тестовых проектах; ревью 20 октября не повторяет runtime/UI-тесты.

Сценарий, относительно которого выставлены приоритеты: универсальный вычислительный ноутбук для исследования данных, настройки экспериментов, визуализации и длительных вычислений, включая ML и обработку аудио. [Удалённое выполнение](../engineering/notebook-remote-ui.md) уже реализовано как preview; совместимость компонентов зависит от конкретных capabilities. Его нельзя целиком считать будущим этапом P2.

## 2. Главные выводы исходного анализа 14 октября

Это историческая мотивация P00/P0/P1. Текущее состояние и оставшиеся пробелы описаны в [ревью 20 октября](notebook-components-p2-review.md).

1. **Палитра сильнее всего покрывает визуальный вывод.** Пять из девяти компонентов относятся к Display. Для графиков, изображений и ML-демонстрации база уже существенная, но табличные результаты приходится смотреть как текст или изображение.
2. **Ввод ограничен общим Input.** Нет выбора из допустимых значений, регулятора чисел, формы с общей кнопкой Apply, пресетов и универсального выбора файла. Изменение нескольких параметров сейчас не имеет общего атомарного применения.
3. **Text / Value объединяет разные задачи.** Числовой показатель, длинный результат и пояснение требуют разных способов представления. Нужны форматируемая метрика, полноценный инспектор и самостоятельный текст доски.
4. **Управление длительной работой слабо компонуется.** Прогресс выводится автоматически над сеткой; сервисы показываются под ней. Пользователь не может свободно расположить отдельные прогресс, статус и управление рядом с нужным графиком.
5. **Данные и их происхождение требуют следующего слоя.** Для таблиц, журналов, истории экспериментов и файлов результата нужны переносимые структурированные снимки и ясные правила хранения. Текстовый preview результата не заменяет такой формат.
6. **Рост каталога потребует изменения самой палитры.** Сейчас плитки имеют ширину 170 pt и лежат в одном HStack. Поиск, сетка с переносом/прокруткой и варианты представления Input позволят расширять каталог без перегруженной полосы.

- **P0 — основа ближайшей версии:** Input Select/Segmented/Radio, Number/Slider/Stepper, Parameter Form и Data Table реализованы 15 октября 2026 года. [Контракт, пример и проверки P0](../engineering/notebook-p0-components.md).
- **P1 — реализован 15 октября 2026 года:** метрики, статус, логи, файлы, действия, управление выполнением, Group, несколько рядов графика, Artifact Browser и Parameter Presets (перенесены из P2). [Контракт и проверки P1](../engineering/notebook-p1-components.md).
- **P2 — локальный набор реализован 20 октября:** аудио и streaming, Audio Input/Recorder, история/сравнение, Range/Date, shared selection, Image Annotator, live logs/tasks, CPU/RAM и Split View. Event Work отложен. [Реализация, проверки и ограничения](notebook-p2-implementation.md).

В оставшемся scope **P2-A** означает первый законченный набор, **P2-B** — следующий после его зависимостей, **P2-C** — специальные сценарии после проверки потребности. Это последовательность, а не сроки.

Приоритет оценивает продуктовую пользу, а не трудоёмкость. Например, Slider проще структурированной таблицы, хотя оба находятся в P0. «Расширение» означает развитие существующего компонента; «Перенос» — размещение на доске уже имеющегося представления приложения; «Новый» — новая возможность палитры.

## 5. Общая основа P00/P0/P1 и её развитие

Это общие возможности, а не дополнительные плитки палитры.

### 5.1. Inputs и формы в обоих режимах исполнения — P0

Обычные project inputs и атомарный batch Apply теперь поддерживаются в in-process и isolated worker. Вся форма проверяется до публикации; изменения передаются одним immutable snapshot и одной волной invalidation. Проверки охватывают оба режима, точные Int64, quiet equal batches и отсутствие запуска на промежуточных/недопустимых значениях формы.

### 5.2. Типизированные привязки и переносимые данные — P0

Существующая база различает input ID, cell/result/binding и channel ID. Сохранить это различие и добавить понятные pickers с совместимостью типов. Недоступный источник должен оставаться видимой сломанной привязкой.

Data Table получила отдельный переносимый формат: схема колонок, скалярные значения, row IDs и признак усечения. Не следует восстанавливать таблицу из Pretty/Inspect: эти представления ограничены по объёму и предназначены для чтения человеком. Через границу worker/UI передавать ограниченные снимки; повторный run должен атомарно заменять committed результаты.

После P1 добавлен [DataTableView](../engineering/notebook-data-table-view.md): объект `notebook.ui` публикуется через `notebook.show` и имеет CSV/Markdown export. Для аудио данные отделены: AudioTrack используется для конверсии/FFT/экспорта независимо от UI; `AudioPlayer.for(track)` задаёт представление для `notebook.show`. **Простой `notebook.player(track, ...)` сохраняется** как сокращение того же пути с теми же defaults, настройками, ID и streaming. Стриминг передаёт дельты PCM подобно Live Chart; команды размещённому player адресуются по hard ID компонента с его областью, отдельно от ID канала. Managed media assets и принятое выделение пока требуют отдельного контракта: локальный путь File Input и transient selection таблицы его не заменяют.

AudioTrack первой версии: `from_file(path)`; `from_data(binary_string, format: "mp3"/"wav"/...)` с обязательным форматом как расширением; `from_pcm(...)` и открытый `stream(...)` с sample format/rate/channels/layout и отдельным interleaving. `format: "wav"` — полный RIFF/WAVE, не raw PCM. В открытый stream данные дописываются chunks до finish; playback не зависит от перерисовки waveform. **Только системные API, без FFmpeg**; поддержанные encoded-форматы определяет клиентская OS. [API и границы сборки](notebook-components-p2-review.md#системный-backend-первой-версии).

### 5.3. Черновик, опубликованное значение и телеметрия — P0

Различать редактируемые поля формы, принятые inputs, последний успешный результат и текущие progress/charts/logs. Новый запуск, ошибка и отмена должны давать понятные состояния. Телеметрия остаётся наблюдаемой после Stop и не считается успешным результатом.

Для Slider режим публикации задаётся явно. Дорогие Manual-ячейки запускаются пользователем; Watch-ячейки используют существующую invalidation-семантику. Изменение оформления, выбор вкладки, поиск и просмотр результата не запускают код.

### 5.4. Палитра и инспектор — P1

В P1 реализованы поиск, фильтр категорий, прокрутка палитры, Undo/Redo и дублирование компонентов/групп. Input имеет варианты в общем семействе; инспектор настраивает совместимые источники и аргументы действий. Сохраняются общие требования:

- Категории Layout / Controls / Display / Services и их спокойные цвета. Отдельная Media-категория для двух аудиоплиток пока не нужна.
- Понятная причина недоступности: нет источника, достигнут лимит, выбранный runtime не поддерживает возможность.
- Выбор источника по имени/подписи и совместимости типов; внутренний ID не подменяет пользовательское имя.
- Состояния передаются текстом/иконкой вместе с цветом; клавиатура и accessibility labels входят в готовность новых компонентов.
- Сетка с переносом плиток и шаблоны компоновки остаются отдельными улучшениями дизайнера; они не должны незаметно считаться выполненными вместе с P1.

## 6. Рекомендуемая последовательность после P1

P00/P0/P1 выполнены. По [ревью 20 октября](notebook-components-p2-review.md) следующий scope:

1. **P2-A: AudioTrack + Audio Player, включая streaming.** Системный backend, независимые данные из файла/бинарной строки/PCM, `AudioPlayer.for` с начальной позицией и `show`, hard ID lookup. Живой PCM channel передаёт begin/append/finish/reset с bounded окнами, backpressure и buffering; один renderer на листе, в cell UI и на доске, local/remote. Публикация не включает звук автоматически.
2. **P2-A: Run History и Runtime Status.** Согласовать snapshots/provenance/retention, переиспользовать remote registry; расширить Status сведениями об окружении и соединении.
3. **P2-B: assets и Audio Input / Recorder.** Переносимые входные данные, импорт и запись в draft, принятый immutable snapshot для Run; затем связанные selection и Experiment Compare.
4. **P2-B: Image Annotator, live logs и Range по сценарию.** Общий контракт разметки, отдельный транспорт логов, атомарные диапазоны вместо новых несвязанных механизмов.
5. **P2-C: специальные сценарии.** Task Monitor, ресурсная телеметрия, Date-time и Split View — после источников данных и подтверждения пользы. Event Work отложен за P2. PCM streaming уже входит в P2-A; произвольный compressed streaming и полная архивная запись потока требуют отдельных расширений.

Для каталога графиков полезнее расширять Figure и Live Chart настройками представления: line, scatter, heatmap и 3D уже частично покрываются plot-пакетом. Toggle существует как представление Boolean Input. Расписание покрыто Periodic Work, измерение блока — Stopwatch; HTTP polling можно первоначально выразить экспортированной функцией. Для аудио waveform, controls и export входят в Audio; Recorder — режим Audio Input. Согласованная модель важнее отдельной плитки на каждую вариацию.

## 7. Сценарии для проверки пользы

| Сценарий | Компоновка | Критерий результата |
| --- | --- | --- |
| Исследование данных | File Input → Data Table → Select/Parameter Form → Figure → Note | Пользователь загружает CSV, выбирает поля и получает воспроизводимый результат через явный Run. |
| ML-эксперимент | Select(device) + Stepper(epochs/batch) → Run → Progress + Status → Multi-series Chart + Metric → Artifact Browser | Параметры принимаются одним набором; выполнение управляется с доски; последний результат имеет понятное происхождение. |
| Периодическое наблюдение | Periodic Work → его Status/History; controller sheet → Live Chart / Data Table | Start/Pause и история сервиса работают независимо от компоновки; данные разных runtime связаны только через явный переносимый контракт. |
| Анализ ошибок модели | Data Table + Image Carousel/Image Annotator + Metric + Note | Пример, предсказание и аннотации связаны стабильным ID, а сохранённые метки можно прочитать при следующем явном запуске. |
| Обработка аудио | Audio Input/Recorder → Parameter Form → Run → Audio original/processed + Metric/Data Table | Принятый клип переносим; Run читает точный snapshot; player работает на листе/доске; WAV export сохраняет явный полный/выделенный диапазон. |
