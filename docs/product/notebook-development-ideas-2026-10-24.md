# Идеи развития Sputnik Notebook

24 октября 2026 года. Предложения по текущему коду и инженерным документам; это идеи, а не обязательства по реализации.

В ноутбуке уже есть доски, 33 компонента, история и сравнение экспериментов, изолированные workers, remote reconnect, управление зависимостями, аудио, спектрограмма и аннотации. Следующий выигрыш — связать эти возможности в понятный исследовательский процесс. Приоритеты ниже — продуктовая оценка, без замеров пользовательской частоты и сроков разработки.

## 1. Объяснение состояния вычисления

**Сценарий:** пользователь изменил параметр и хочет понять, почему результат не обновился.

Добавить действие «Почему такой результат?» у ячейки. Показывать цепочку её зависимостей, последний Run, версию параметров, изменённый источник и конкретную причину блокировки: устаревший Manual-поставщик, неприменённый модуль, новое окружение или недоступный host. Дать переход к причине и явное действие пересчёта.

Первый этап: компактная панель причин и переход к блокирующей ячейке; затем интерактивный граф. Просмотр панели не исполняет код. Основа уже есть в dependency graph, scheduler и метаданных результатов.

**Проверяемый результат:** в цепочке из трёх ячеек можно объяснить актуальность каждого результата и устранить блокировку без Restart Worker.

## 2. Воспроизводимый пакет эксперимента

**Сценарий:** успешный эксперимент нужно повторить на другой машине через месяц.

Развить существующие Run History / Experiment Compare: сохранять manifest запуска с ревизией языка, runtime/ABI, Sputnik/Python/Ruby lockfiles, seed, inputs, хешами входных ресурсов и ссылками на outputs. Действие «Повторить в чистом worker» создаёт отдельный запуск из этого manifest. Перед стартом показывает отсутствующие зависимости и ресурсы.

Первый этап: export/import manifest плюс проверка комплектности. Следующий: переносимый `.sputnikbook` с выбранными ресурсами и закреплёнными пакетами. Живой heap и состояние внешних сервисов не входят в обещание воспроизводимости; это фиксируется в manifest.

**Проверяемый результат:** чистый worker на втором host повторяет детерминированный пример с теми же inputs и совпадающим результатом.

## 3. Серии экспериментов поверх существующего Compare

**Сценарий:** проверить несколько learning rates, seed или порогов и выбрать лучший результат.

Добавить «Серию запусков»: набор параметров, экспортированная функция или ячейка, лимит параллельности, host и метрики. Каждый вариант получает immutable inputs и отдельную запись истории. Уже существующий Compare становится таблицей серии с сортировкой по метрике, графиком и переходом к конкретному запуску.

Первый этап: явная конечная сетка и последовательная очередь на сервере; затем bounded concurrency и профили CPU/GPU. Закрытие клиента не меняет очередь. Остановка серии и остановка текущего запуска — отдельные команды. По умолчанию варианты изолированы; повторное использование worker требует явной политики состояния.

**Проверяемый результат:** серия из десяти вариантов завершается без клиента, сохраняет источники и параметры каждого варианта, допускает отмену оставшейся очереди.

## 4. Последовательное выравнивание local и remote

**Сценарий:** рабочий локальный пример переносят на сервер без ручного переписывания книги.

Закрывать разрывы по отдельным capabilities: project inputs и их атомарный Apply, idle Watch, directory/dependency bundles, затем module Run и board services. Каталог пакетов и managed Python/Ruby environments уже есть; их следует включить в общий путь подготовки окружения.

Первый этап: inputs + Watch для небольшого эталонного notebook. Перед Run интерфейс показывает точный список неподдерживаемых возможностей и доступное действие; результат всегда сохраняет host/revision/epoch.

**Проверяемый результат:** один и тот же notebook с inputs, зависимой Watch-ячейкой и небольшим графиком проходит одинаковый набор сценариев на local и remote.

## 5. Серверный Periodic Work, затем Event Work

**Сценарий:** опрашивать источник данных или регулярно строить отчёт после закрытия приложения.

Перенести расписание существующего Periodic Work в агент: durable Start/Pause, версия функции и окружения, один активный tick, пропуск пересечений, ограниченная история и независимый Stop. Открытие книги не включает расписание. После рестарта агента нужна явная политика восстановления; пропущенные ticks не превращаются в очередь.

После этого добавить Event Work для конкретных источников: изменение ресурса, поступление сообщения, завершение другого Run. Нужны debounce и идентификатор события, чтобы повторная доставка не запускала вычисление дважды.

**Проверяемый результат:** расписание работает без клиента, Pause переживает перезапуск gateway, один event ID не создаёт два Run.

## 6. Хранилище больших данных и артефактов

**Сценарий:** работать с датасетом, моделью или аудио, которое не помещается в текущие лимиты snapshot.

Отделить небольшие документы от больших blobs. Добавить загрузку частями с возобновлением, хеширование содержимого, дедупликацию и реестр артефактов с размером, владельцем и источником Run. Развить существующую уборку orphan environments и архивирование media до явной политики retention всего проекта.

Первый этап: артефакты outputs и страница «Место на диске» с предварительным просмотром освобождаемого объёма. Pin, активный Run, открытый worker и ссылки из истории удерживают данные от GC. Удаление показывает, какие исторические результаты потеряют доступ к файлу.

**Проверяемый результат:** прерванная загрузка продолжается, одинаковый blob хранится один раз, GC сохраняет все закреплённые и используемые ресурсы.

## 7. Редактор, который объясняет Sputnik

**Сценарий:** найти ошибку до долгого remote Run и быстро освоить новые конструкции языка.

Добавить контекстные сигнатуры, переход к определению, поиск использований и диагностику без исполнения. Показывать доступные методы и минимальные примеры для `then`, `for`, `transformed*`, BigInt и ByteBuffer. Связать F1 и ошибки с уже спроектированной встроенной справкой и запускаемыми sample notebooks.

Первый этап: точный source span ошибки, переход из worker diagnostics к ячейке/модулю и контекстная справка. Диагностику привязывать к версии текста; устаревший ответ не должен подсвечивать новый источник. Автодополнение не инициализирует пользовательские модули.

**Проверяемый результат:** ошибка удалённого модуля открывает правильный файл и строку; справка и hover работают без создания runtime.

## 8. Длительные задачи с явными checkpoints

**Сценарий:** обучение или обработку данных нужно продолжить после обновления core либо потери сервера.

Ввести API пользовательского checkpoint: сериализуемое состояние алгоритма, позиция во входных данных, seed/state генератора, версия схемы и artifact references. Публикация атомарна. «Продолжить с checkpoint» создаёт новый Run и явно показывает родительский Run; вычисление не маскируется под продолжение прежнего heap.

Первый этап: sample с пакетной обработкой и ручными Save/Resume. Затем checkpoints в сериях экспериментов и перед запланированным обслуживанием. Совместимость версии алгоритма проверяется до исполнения; для внешних side effects требуется отдельный контракт идемпотентности.

**Проверяемый результат:** после остановки worker пример продолжает обработку с последнего подтверждённого checkpoint и выдаёт тот же итог, что непрерывный запуск.

## Предлагаемый порядок

| Очередь | Работа | Почему сейчас |
| --- | --- | --- |
| 1 | Объяснение состояния + переходы из diagnostics | Уменьшает неопределённость в ежедневной работе; использует уже существующие метаданные. |
| 2 | Manifest эксперимента + минимальная local/remote parity | Делает проверяемыми переносимость и повторение результатов. |
| 3 | Серии запусков + Compare | Превращает готовые историю, inputs и remote core в законченный экспериментальный процесс. |
| 4 | Большие артефакты + retention | Снимает ограничения объёма данных и роста server state. |
| 5 | Серверные services и checkpoints | Расширяет длительную автономную работу после стабилизации окружений и хранения. |
