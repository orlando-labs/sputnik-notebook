# Проект встроенной справки Sputnik Notebook

Дата: 20 октября 2026 года. Уточнение требований к примерам: 21 октября 2026 года. Статус: проект для обсуждения.

Документ определяет содержание, интерфейс и способ реализации справки. Он не добавляет окно справки, статьи, поисковый индекс или изменения в приложение. Все новые названия модулей, файлов и маршрутов ниже — предложения.

## 1. Решение

Сделать встроенную офлайн-справку с тремя связанными способами чтения:

1. **Руководства по задачам:** как создать лист, организовать вычисления, настроить доску, понять изменение результата.
2. **Каталог компонентов:** назначение, источники данных, все настройки и поведение каждого компонента.
3. **Справочник API:** точные вызовы Sputnik, типы данных, ограничения и примеры связи кода с интерфейсом.

Это один набор материалов с перекрёстными ссылками. Из статьи о Live Chart можно перейти к настройкам канала, `publish_point` и сценарию наблюдения за вычислением; из справочника функции — обратно к компоненту.

**Обязательное требование: у каждого компонента есть своя отдельная example-книга `.sputnikbook`, покрывающая его основные пользовательские сценарии.** Для текущего каталога это минимум 33 самостоятельные книги. Карточка компонента, API-примеры и книга связаны между собой; наличие компонента в общей демонстрационной книге не заменяет его собственного примера.

Основной язык первой версии — русский. Названия кнопок приводятся как в текущем интерфейсе: **Save Current Tab**, **Apply Saved Modules**, **Components…**. Английские названия компонентов и API участвуют в поиске вместе с русскими пояснениями. Идентификаторы статей не зависят от языка; полноценный английский перевод можно добавить позднее без изменения ссылок.

## 2. Основание и границы

Справка предназначена прежде всего для текущего macOS-приложения. Она объясняет локальное и удалённое выполнение с явными различиями возможностей. Терминальный `isputnik` упоминается в совместимости формата и ссылках на отдельные материалы; его клавиши не смешиваются с командами GUI.

У проекта уже есть инженерные документы и исполняемые примеры. Их следует использовать как исходный материал, но организовать пользовательскую справку вокруг задач, а не этапов P00/P0/P1/P2. Исторические документы содержат устаревшие ограничения: например, старый раздел о досках не описывает все нынешние действия и управление выполнением.

При подготовке каждой статьи сверяются текущий код, соответствующие тесты, актуальный контракт и пример. Противоречие оформляется как вопрос к реализации, а не переносится в справку. Само наличие теста не означает, что он прошёл в данной сборке.

Текущая опора для объёма:

- Общий каталог `NotebookComponentTool.all` содержит **34 карточки**: 33 типа компонентов и пресет Image Annotator.
- Внутри code-ячейки авторские pre/post-компоненты сейчас ограничены шестью типами: Input, Parameter Form, Live Chart, Metric, Image, Data Table. Автоматический Progress описывается отдельно.
- Image Annotator — режим Image/Image Carousel с отдельной карточкой палитры; вместе с Audio Annotator он находится во вкладке Annotations. Multi-series — настройка Live Chart; варианты Input — настройки одного семейства. Audio Annotator имеет собственный тип.
- Список remote-возможностей отличается от local. Например, поддержка cell inputs не означает поддержку всех project inputs, Action или Periodic Work на сервере.
- В меню приложения сейчас нет полноценного Help. Существующие `.help(...)` — краткие подсказки, которые можно связать с новой справкой.

## 3. Доступ к справке и устройство окна

### Точки входа

| Место | Предлагаемое действие | Что открывается |
| --- | --- | --- |
| Меню Help | «Справка Sputnik Notebook» | Главная страница либо последняя открытая статья |
| Стартовый экран | «Начать работу» | Первое создание книги и листа |
| Заголовок листа | «О листах и выполнении» | Листы, Save / Apply / Run, Manual / Watch |
| Палитра Board Designer | Кнопка справки у выбранного типа | Карточка этого компонента |
| Инспектор компонента | «О компоненте» | Карточка с выделенным текущим разделом |
| Сложная настройка | Ссылка или кнопка рядом с подписью | Конкретная настройка, например атомарный Apply |
| Components… | «Компоненты ячейки» | Pre/post, локальные параметры, область источников |
| Worker Settings / Servers / настройки книги | Кнопка справки | Соответствующая группа настроек |
| Известное состояние или ошибка привязки | «Подробнее» | Причина, способ исправления и условия повторного запуска |

Справка открывается в отдельном переиспользуемом немодальном окне. Редактор доски и черновики остаются открыты; окно справки доступно во время Run и без открытой книги. Оно не занимает вкладку листа и не становится частью проекта.

Окно содержит слева оглавление и поиск, справа статью. У статьи есть хлебные крошки, локальное оглавление длинного материала, переходы назад/вперёд, копирование фрагментов кода и блок «Связанные материалы». В узком окне оглавление сворачивается. Поддерживаются светлая/тёмная темы, увеличение текста, выбор текста и клавиатурная навигация.

Короткая подсказка отвечает на один вопрос о поле. Полная статья объясняет правила и последствия. Не помещать всё описание в tooltip.

Контекстное открытие получает только известный маршрут и необязательный идентификатор раздела. Оно не читает значения пользовательских параметров и не запускает вычисления. В каждой карточке компонента есть действие «Открыть пример»: пользователь выбирает место для рабочей копии поставляемой `.sputnikbook`, затем она открывается с обычной защитой несохранённых изменений. Эталон внутри приложения остаётся неизменным. Открытие книги не запускает её; Run, запись аудио и Start сервиса остаются явными действиями. В справке нет кнопки исполнения кода в текущей книге.

### Главная страница

Показать поиск и шесть входов: «Начало работы», «Листы и выполнение», «Изменения и результаты», «Доски», «Компоненты», «API». Ниже — несколько типовых задач: собрать форму параметров, вывести таблицу, построить живой график, понять устаревший результат, подключиться к серверу.

## 4. Оглавление

### 4.1. Начало работы и основные понятия

- Книга `.sputnikbook`: листы, модули, доски, параметры и ресурсы.
- Первый сценарий: создать книгу → лист → code-ячейку → Run → сохранить → открыть снова.
- Чем отличаются code-ячейка, текстовый блок, модуль и доска.
- Что хранится в проекте, что существует только в текущем сеансе, что сохраняется в истории.

### 4.2. Листы: создание и правила работы

Последовательность руководства: **Sheets → + → идентификатор → первая ячейка → явный Run**. Отдельно объяснить, что создание листа сохраняет структуру, но не исполняет код. Правила идентификаторов и сообщения об ошибках сверить с `ProjectTabs::create_sheet` / `validate_new_tab_id`, а не переносить ограничения module ID по аналогии.

Обязательные темы:

- Идентификатор и заголовок листа, доступные операции над листами в текущей версии.
- Добавление, удаление и перемещение code/text-ячеек; выбор ячейки и Run All.
- Порядок чтения переменных: ближайшая предшествующая ячейка с нужным именем; повторная публикация и затенение.
- Постоянный Hard ID и видимый номер ячейки. Перемещение меняет номер, сохраняя привязки; редактирование Hard ID объясняется отдельно.
- Разрешённый профиль code-ячейки; определения классов и функций размещаются в модулях согласно текущим ограничениям компилятора.
- Изоляция runtime разных листов. Общие project inputs не означают общий heap или прямой доступ к переменным другого листа.
- Save Current Tab / Save All Tabs, Apply Saved Modules и Run: разные действия и разные последствия.
- Модули, auto-import и Dependencies; явные импорты локальны ячейке. Обновление исходников пакета принимается через Apply, автоматического наблюдения файлов пакетов нет.
- Текстовые блоки, Markdown, `{{name}}`, доступность опубликованных переменных и отсутствие исполнения при просмотре.
- Components…: pre/post, локальные inputs, сохранение интерфейса и условия сворачивания исходника.

### 4.3. Изменения, зависимости и результаты

Раздел должен разводить четыре понятия: несохранённое редактирование документа, устаревание вычисленного результата, реактивное обновление Watch и сохранённую историю запусков. Удалённые ревизии проекта описываются дополнительно. Это не обещание отдельного редактора diff или режима рецензирования правок.

| Событие | Что объясняет справка |
| --- | --- |
| Редактирование кода | Где находится черновик; чем несохранённость отличается от необходимости пересчёта; почему виден прежний результат |
| Save | Как сохраняется источник; почему сохранение само по себе не подтверждает актуальность вычисления |
| Apply параметров | Валидация целого набора, принятый снимок, точные читатели, Watch и Manual, поведение неинициализированного листа |
| Изменение зависимости | Как распространяется устаревание; почему stale Manual-поставщик блокирует зависимые Watch-ячейки |
| Изменение модулей или пакетов | Разница сохранённых и применённых исходников; успешный Apply создаёт новое окружение, Watch/Manual следуют своим правилам |
| Ошибка, Stop, Force Stop | Последний успешный результат, частичная телеметрия, потеря runtime и необходимость Restart |
| Просмотр истории | Какие данные зафиксированы, ограничения снимка, Pin / retention / export; просмотр не исполняет код |
| Restore parameters | Что именно восстанавливается, проверка совместимости и отсутствие автоматического Run в этом действии |
| Remote conflict / reconnect | Черновик клиента, серверная ревизия, версия параметров и источник результата; разрешение конфликта и повторное подключение |

Схему Manual / Watch объяснить на цепочке из трёх ячеек. Для каждого состояния дать: видимую подпись в текущем UI, причину и следующее действие. Основные состояния: ещё не выполнялась, актуальный результат, требует пересчёта, заблокирована зависимостью, выполняется, ошибка, отменена, прежний результат, окружение устарело.

Сохранённые defaults, редактируемый draft и принятые runtime-значения показываются раздельно. Новый Run читает неизменяемый снимок. Принятые параметры не откатываются из-за последующей ошибки вычисления. Точное поведение Restore и обычного Apply описывается отдельно: одинаковое слово «применить» не гарантирует одинаковый запуск Watch.

История запусков — существующая отдельная возможность с условиями включения, ограничениями и различиями local/remote; это не полный журнал всех пользовательских правок. Если потребуется история исходников с diff, она проектируется отдельной задачей.

### 4.4. Доски

- Создание доски и выбор управляющего листа.
- Design и использование сохранённой доски; черновик, Save Board и Cancel.
- Палитра Layout / Controls / Display / Services, поиск и добавление компонента.
- Строки, ширина/span, высота, выравнивание, перенос компонентов, Undo/Redo и дублирование.
- Tabs, Group / Accordion и Split View: вложенные panel grids и правила контейнеров.
- Типы привязок: project input, ячейка, опубликованная переменная, канал; правила области видимости и причины сломанной привязки.
- Run Button, Action Button и Execution Controls: что именно исполняется и где находится состояние.
- Periodic Work: отдельный сервис, расписание, Start/Pause/Stop и собственная история.
- Selection и аннотации: черновой выбор, явный Apply, стабильная identity ресурса, чтение следующей ячейкой.
- Переносимость: внешняя ссылка File Input, managed media, зависимости и артефакты результата.

Изменение компоновки, открытие доски и просмотр данных не считаются командами исполнения. Запуски через кнопки, изменение принятых inputs и сервисы объясняются каждый по своему контракту.

### 4.5. Настройки приложения и окружения

Отдельные страницы: Settings приложения, настройки книги, Worker Settings, Servers. Для каждой настройки указывать область действия, место хранения, необходимость сохранения/перезапуска и влияние на выполнение. Минимальный состав: тема, замена имён греческих букв, сохранение предыдущего результата, runtime grants, local/remote host, перезапуск worker, управление неиспользуемыми media.

Это настройки другого уровня, чем поля компонента. Например, сохранение предыдущего результата относится к книге, а выбранный канал — к экземпляру компонента.

### 4.6. Решение проблем

Короткие диагностические маршруты: «результат не изменился», «Watch не запускается», «канал пуст», «источник удалён», «модуль изменён, но поведение прежнее», «файл недоступен на сервере», «параметры не принимаются», «результат относится к старой ревизии», «после Stop видны точки графика», «не удаётся свернуть исходник».

Каждая страница заканчивается проверяемым действием пользователя и ссылкой на соответствующее правило. Кнопки и состояния, отсутствующие в текущей версии, не предлагать.

### Шаблон карточки

1. **Назначение:** что видит или делает пользователь; подходящий сценарий.
2. **Доступность:** доска / pre-cell / post-cell / автоматический вывод; отдельно local/remote и ограничения версии.
3. **Быстрое подключение:** минимальные шаги в UI и код, если компонент требует публикации данных.
4. **Источник и привязка:** тип, область, идентификаторы; что происходит при отсутствии источника.
5. **Настройки:** полная таблица доступных полей текущего инспектора, включая условно видимые.
6. **Поведение:** draft/Apply, выполнение, изменение данных, ошибка, Stop, reopening, сохранение.
7. **API:** ссылки на вызовы и форматы; для чистого Layout явно указать отсутствие обязательного программного вызова.
8. **Пример и диагностика:** обязательная собственная example-книга `.sputnikbook`, список основных сценариев с ожидаемыми результатами, действие «Открыть пример», частые ошибки и связанные статьи.

Для каждой настройки таблица фиксирует: подпись в UI, внутренний ключ при необходимости, смысл, тип/единицу, начальное значение или правило автоматического выбора, допустимые значения, условие доступности, момент применения и место сохранения. Ограничения и defaults берутся из текущего кода. Значение «авто» объясняется правилом, а не придуманным числом.

Общие поля ID / Title / Row / Span / alignment описываются один раз; карточки ссылаются на общую таблицу и добавляют свои отличия. Настройки из кода и Board Designer показываются с правилами приоритета, например для Audio Player Show waveform. Временный zoom графика и сохранённые пределы осей также объясняются раздельно.

Варианты Input получают подразделы одной карточки. Image Annotator и Multi-series получают собственные якоря и поисковые имена. AudioTrack описывается как объект данных в API; наличие player-компонента не делает трек отдельной плиткой палитры.

### Отдельные example-книги компонентов

Предлагаемое место: `tools/notebook-macos/Samples/Components/<kind>.sputnikbook/`. Каждая книга — полноценный проект с собственным `project.json`, учебными текстовыми блоками, кодом, досками и необходимыми небольшими ресурсами. Путь привязан к стабильному kind, например `input.sputnikbook` или `live_chart.sputnikbook`. Вспомогательные компоненты допустимы, но у каждой книги есть один основной компонент; один путь не может засчитываться за примеры нескольких типов.

Книги не зависят от предварительного запуска других примеров. Существующие комплексные Samples можно использовать как материал и дополнительные сквозные сценарии. Все необходимые модули и учебные данные входят в книгу либо имеют явно описанную поставляемую зависимость. Жёсткие пути к checkout автора, личные данные, обязательные внешние сервисы и тяжёлые загрузки исключаются. Для File Input книга содержит небольшой учебный файл и шаг его выбора; это демонстрирует контракт внешнего пути, а не подменяет его переносимым media input.

Единая структура книги:

1. **Начало:** назначение компонента, предварительные условия, ссылка на справку и последовательность первого запуска.
2. **Основные сценарии:** отдельные подписанные листы или блоки с исходными данными, действиями пользователя и ожидаемым видимым результатом. Одного статического экземпляра компонента недостаточно.
3. **Настройки и обновление:** практически значимые варианты, смена источника/параметров, повторный Run или Apply по контракту компонента.
4. **Состояния и ограничения:** ожидание данных, stale, валидация, Stop или недоступный источник — там, где это относится к компоненту. Намеренные ошибки изолированы в отдельном Manual-сценарии и не ломают первый запуск.
5. **Повторение:** как вернуть исходное состояние и пройти сценарий заново; что сохранится при reopening.

Для шести поддержанных cell-типов одна и та же книга содержит примеры на доске и в pre/post-областях ячейки. Варианты одного типа входят в его книгу: стили Input, Multi-series Live Chart, annotation mode Image/Image Carousel. Audio Annotator получает собственную книгу. Поддержанные remote-сценарии описываются и проверяются отдельно от local; если сервер не поддерживает возможность, это указывается явно.

Ручные сценарии записи, экспорта и интерактивных жестов обозначаются явно; факт наличия книги не засчитывается как проверка её сценариев.

Компоненты истории сами создают учебные запуски по инструкции; готовая чужая runtime-история не является обязательным условием. Сброс состояния описан для каждой книги.

## 6. Справочник API

### Состав

| Семейство | Что документировать |
| --- | --- |
| Параметры | `notebook.input`, `notebook.cell_input`; типы, область, default и принятый snapshot |
| Публикация результата | `notebook.show`, поддержанные представления, ID/caption, result против отдельного display |
| Таблицы | `DataTableView`, входные формы данных, колонки, `to_csv`, `to_markdown`, ограничения снимка |
| Графики | `publish_point`, каналы и multi-series; отдельно Figure из plot-пакета и условия зависимости |
| Изображения | `image`, `publish_image`, `publish_images`, `add_image`, `clear_images`, `read_image`, `read_images` |
| Выбор и разметка | `notebook.selection`, `notebook.annotations`, `notebook.audio_annotations`, схемы возвращаемых данных |
| Аудио | `AudioTrack`, `AudioPlayer.for`, `notebook.player`, lookup/control, PCM append/finish/reset, импорт и снимок входа |
| Наблюдение | Действующий API progress и `Stopwatch.measure`; различие результата и текущей телеметрии |
| Действия и сервисы | Контракт экспортированной module-функции, поддержанные аргументы, изоляция runtime, вызов через UI |

Точные имена и импорты проверяются по реализации перед написанием страниц. Публичный API формируется из Sputnik-модулей **и** нативной регистрации: например, `Stopwatch` не следует искать только в строке `export` файла `notebook_ui.s`. Private worker protocol и bridge API не включаются в пользовательский справочник.

### Шаблон API-страницы

- Полное имя, импорт и точная сигнатура, включая именованные аргументы.
- Типы аргументов, значения по умолчанию, единицы и ограничения.
- Возвращаемое значение и схема данных.
- Необходимый контекст: активная ячейка, модуль, самостоятельное использование вне notebook.
- Побочные эффекты: публикация, замена/добавление, чтение accepted snapshot.
- Lifecycle: новый Run, Stop, ошибка, сброс, сохранение и поддержка remote.
- Короткий самостоятельный пример с перечисленными предварительными настройками.
- Типовые ошибки и ссылки на компоненты-потребители.

Примеры должны объяснять обе стороны соединения: что настроено в UI и какой ID использует код. Минимальная иллюстрация будущего формата:

> В Board Designer добавьте Live Chart и задайте Channel ID `loss`. В code-ячейке управляющего листа опубликуйте точки и выполните её. В Components… тот же код работает с Live Chart своей ячейки; совпадение имени канала другой ячейки не соединяет их.

```sputnik
from notebook.ui import publish_point

publish_point("loss", 0, 1.0)
publish_point("loss", 1, 0.7)
```

У примера есть ожидаемый результат: две точки одного канала. Он не обещает сохранения runtime-точек в manifest и ведёт к описанию лимитов и экспорта.

Для конфигурируемых только через UI элементов не изобретать конструкторы вроде `notebook.create_board(...)`. JSON проекта — отдельная расширенная справка по формату с предупреждением о версии; он не заменяет руководство по настройкам и публичный API компонентов.

## 7. Поиск и контекстные ссылки

Поиск локальный, без сети и анализа пользовательских книг. Индекс содержит заголовки, подзаголовки, текст, подписи настроек, имена API и вручную заданные синонимы. Примеры запросов: «лист», «sheet», «живой график», «Live Chart», `publish_point`, «устарело», «Watch», «применить параметры».

Ранжирование: точное имя API/компонента → заголовок → настройка или синоним → основной текст. Результат показывает тип материала и найденный фрагмент; переход открывает конкретный раздел. Точное совпадение работает и без русской морфологии; для первой версии достаточно нормализации регистра, разбиения слов и редакторских синонимов. Полноценную морфологию добавлять по результатам проверки запросов.

Стабильные маршруты, например `guides/sheets`, `guides/changes`, `components/live-chart`, `api/notebook-ui/publish-point`, отделены от файловых путей. Настройка может иметь маршрут `components/live-chart#settings-channel`. Переименование заголовка не ломает ссылку; для смены route сохраняется alias.

В UI передаются route/anchor из общего каталога ссылок. Неизвестный anchor открывает начало существующей статьи; неизвестный route показывает поиск с понятным сообщением. Отсутствие контекста книги не мешает чтению.

## 8. Организация материалов и техническая реализация

### Исходники

Предлагаемая структура в репозитории `sputnik-notebook`:

```text
docs/help/
  manifest.json                 # порядок разделов, aliases, версия контента
  ru/guides/*.md                # задачи и правила
  ru/components/*.md            # карточки 33 типов и разделы вариантов
  ru/api/*.md                   # публичные вызовы и схемы данных
  ru/troubleshooting/*.md       # диагностика
  metadata/components.json      # kind → route, области, настройки, источники
  metadata/api.json             # symbol → route, источники и примеры
  metadata/examples.json        # kind → отдельная книга, сценарии и проверки
  assets/                       # только нужные иллюстрации

tools/notebook-macos/Samples/Components/
  <kind>.sputnikbook/           # отдельная example-книга для каждого типа
    project.json
    modules/                   # если нужны учебные функции
    assets/                    # учебные данные; images/audio по контракту книги
```

Markdown содержит небольшой front matter: стабильный ID, заголовок, язык, вид материала, ключевые слова, связанные страницы и ссылки на источники проверки. Каталожные метаданные задают порядок и покрытие; текст не хранится второй копией внутри Swift-кода. Один экземпляр статьи обслуживает полное окно и контекстный переход.

Инженерные документы остаются контрактами разработки, а help — пользовательским представлением. Общие правила не копируются по карточкам: например, статья об атомарном Apply едина для формы, presets и range с явными исключениями. Скриншоты дополняют текст, но не являются единственным носителем правил и названий настроек.

### Сборка

Последовательность: Markdown + метаданные + example-книги → проверка ссылок/покрытия и проектов → структурированные блоки статей + поисковый индекс + каталог примеров → ресурсы `.app`. Каждая example-книга включается целиком с нужными модулями и ресурсами.

На этапе сборки поддержанный набор Markdown преобразуется в блоки: заголовки, текст, списки, таблицы, примечания, изображения и код. Renderer не исполняет HTML или Sputnik. Для первой версии достаточно небольшого фиксированного формата; выбор парсера решается отдельным техническим шагом после проверки существующих зависимостей.

В поставку входят готовые данные; Python/Node и исходный checkout для чтения справки пользователю не нужны. Контент получает версию/идентификатор сборки и сведения о совместимом runtime. Справка поставляется с приложением; онлайн-обновления, отдельный сайт и серверный поиск не требуются.

### Нативные части приложения

Предлагаемые роли:

- `NotebookHelpStore`: загрузка статей, routes/anchors/aliases и версии.
- `NotebookHelpSearch`: поиск по готовому индексу.
- `NotebookHelpView`: оглавление, статья, навигация, selectable code и копирование.
- `NotebookHelpCoordinator`: отдельное окно и открытие контекстного адреса.
- Общий каталог help-ссылок: соответствие component kind / настройка / состояние маршруту.

Предпочтителен SwiftUI/AppKit reader со структурированными блоками и переиспользованием подсветки Sputnik. Выделяемые текстовые блоки, таблицы и ссылки нужно проверить небольшим техническим прототипом до полной вёрстки. Сам прототип не входит в текущую задачу.

Справка не меняет schema `.sputnikbook`, не добавляет данные в пользовательские проекты и не зависит от живого worker. Она получает текущий backend/capabilities только для пояснения доступности. Если сервер не сообщает возможности, показывается «поддержка не подтверждена», а не автоматическое предположение о поддержке.

Контекстные тексты и статическая матрица совместимости берутся из поставляемого контента. Проверенный ответ runtime может уточнить доступность в текущем соединении; адрес статьи остаётся тем же. Сетевые запросы ради открытия справки не требуются.

## 9. Поддержание актуальности и проверка

Для изменения компонента, инспектора или API в review проверяются соответствующая статья, метаданные покрытия и пример. У каждой статьи указаны исходники и версия/дата последней сверки. Не обозначать материал «проверенным» только по дате изменения файла.

Будущая проверка сборки должна находить:

- Тип из `NotebookComponentTool.all` без карточки; лишние типы и дубли маршрутов.
- Расхождения документированной доступности с allowlist компонентов ячейки.
- Настройку из поддерживаемого реестра полей без описания, в том числе условно видимую.
- Публичный API из согласованного списка без страницы или с недоступной ссылкой.
- Битые внутренние ссылки, anchors, aliases и пути ресурсов.
- Компонент без собственной example-книги, совпадающие `book_path` у разных основных компонентов, отсутствующий `project.json` или неуказанную зависимость.
- Основной сценарий из реестра без инструкции, ожидаемого результата или проверки; отсутствие board/cell-покрытия там, где поддерживаются оба контекста.
- Несоответствие примеров в исходниках и ресурсах `.app`; битое действие «Открыть пример» или потерянные учебные ресурсы.

Каталог типов уже централизован, но исчерпывающего машиночитаемого описания всех inspector-полей и публичных сигнатур сейчас нет. В первой версии их реестр составляется по коду и проходит review; проверка подтверждает покрытие этого реестра, а не автоматически доказывает отсутствие любых недокументированных полей. Перенос настроек в общую schema — отдельное возможное улучшение.

Исполняемые примеры оформляются с входными данными и ожидаемым эффектом. Headless-проверка покрывает чтение параметров и форматы публикаций; UI-проверка — фактическое появление и привязки. Аудио, запись, remote и зависимости запускаются в подходящем окружении; пропущенный сценарий явно помечается. Просмотр справки отдельно проверяется на отсутствие Run, изменения книги и потери черновика.

| 2. Вертикальный прототип | Help window, статья о листах, карточка и отдельная example-книга Live Chart, API-страница, поиск и переход к настройке | Читается без сети/worker; пример открывается рабочей копией; основные сценарии Live Chart проверены |
| 3. Основные руководства | Листы, Save / Apply / Run, изменения/Watch, доски, параметры, выполнение | Пользователь проходит сценарии с нуля и понимает stale/Manual без чтения исходников |
| 4. Полный каталог и API | Все карточки, условные настройки, API, диагностика и минимум 33 отдельные example-книги | У каждого типа своя книга; основные сценарии проверены в заявленных режимах |
| 5. Проверка поставки | Проверки в сборке, статьи и example-книги в `.app`, навигация, темы и доступность | Работает установленная `.app` без checkout; все примеры открываются рабочими копиями без исполнения |

В первую полезную поставку входят этапы 1–3 и явно обозначенный доступный каталог. Каждая включённая карточка уже должна иметь собственную example-книгу с основными сценариями. Полноценной справкой по всем компонентам продукт считается после этапов 4–5, включая полный комплект отдельных книг. Сроки оцениваются после инвентаризации полей и сценариев; число плиток само по себе не определяет объём.

## 11. Критерии готовности

1. Пользователь создаёт лист, выполняет ячейку и сохраняет книгу по руководству; различает лист и модуль.
2. По изменённому параметру или устаревшему результату находит причину, понимает поведение Manual/Watch и нужное действие.
3. По каждому компоненту доступны назначение, все поддержанные настройки, источники и правила сохранения/исполнения.
4. Из настройки открывается нужный раздел; по имени API находится сигнатура и пример подключения к UI.
5. Контекст доски и ячейки, local и remote описан без переноса неподдержанных возможностей.
6. Просмотр истории, сохранение документа, применение параметров и пересчёт объясняются как отдельные действия.
7. Справка доступна офлайн, во время Run и без проекта; сохраняет черновики и не исполняет пользовательский код.
8. Добавление нового типа или изменение описанных полей сопровождается обновлением материалов и проверяемого реестра.
9. У каждого компонента есть собственная отдельная `.sputnikbook` с основными пользовательскими сценариями: минимум 33 книги для текущего каталога. Общие демонстрационные проекты дополняют этот набор.
10. Для каждого основного сценария указаны входные данные, действия и ожидаемый результат; поддержанные варианты на доске и в ячейке покрыты в книге соответствующего компонента.
11. Из карточки открывается рабочая копия нужной книги со всеми учебными ресурсами; сценарии можно повторить с исходного состояния без checkout и запуска других примеров.
